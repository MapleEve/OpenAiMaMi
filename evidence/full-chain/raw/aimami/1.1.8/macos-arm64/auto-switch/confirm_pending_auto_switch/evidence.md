## Confirmed (live HexRays decompile this session, cross-checked against 1.0.9 baseline files on disk)

1. `confirm_pending_auto_switch`'s "no pending request" path is byte-identical in behavior to 1.0.9: same static error string `"No pending auto-switch request"` (30 bytes), same `load_pending_auto_switch` fs-read + serde_json parse shape (VA moved from 0x1005ea840 in 1.0.9 to 0x10052b920 in 1.1.8 due to relinking only).
2. 1.1.8 inserts an entirely new "candidate credential freshness gate" between `load_pending_auto_switch` returning `Some` and the final `switch_account` call. This gate does not exist anywhere in the 1.0.9 call tree, which went straight from `load_pending_auto_switch`'s `Some` branch to `switch_account`.
3. Three brand-new user-facing error strings were found and confirmed via direct string literal in the decompiled body (not inferred from symbol names): `"Candidate account no longer exists locally"` (42B), `"Candidate account credentials have expired since the suggestion was made"` (72B), `"Candidate token is no longer valid, please try another account"` (62B). None of these three strings exist anywhere in the 1.0.9 macOS raw evidence for this command.
4. The freshness gate performs a real network round-trip: `oauth_refresh::ensure_fresh_token` builds a `reqwest::blocking::Client` request to `https://auth.openai.com/oauth/token` with `grant_type=authorization_code` + `code_verifier` form fields and header `User-Agent: AiMaMi/1.1.8` (string literal confirmed in the function's string pool), sends it, and parses a JSON response via serde_json. This is a synchronous/blocking call (not an async `::poll` state machine), so red line 13's async-unwrap requirement does not apply here.
5. On a successful token refresh, the refreshed `AuthFile` is serialized and persisted back to disk via `relay::atomic_write::write_atomic` — confirmed via direct decompile of `write_atomic` to be the standard temp-file + `fsync` + `rename(2)` atomic-write pattern (`Path::parent` → `DirBuilder::_create` → temp filename from `process::id`+`uuid::v4` → `OpenOptions::_open` → `write_all` → `File::sync_data` → `std::sys::fs::rename` → `sync_parent_dir`, with `remove_file` cleanup on any failure step).
6. `switch_account` (the actual account-switch action) is unchanged in its core responsibility vs 1.0.9 — `load_registry` → `ensure_directories` → `fs::copy` (per-account state snapshot) → `persist_registry` (writes the updated active-account registry) → `CoreEnvelope::ok_with_warnings` (success envelope). It is now reachable only after the new freshness gate passes.
7. `clear_auto_switch_snooze` (new call site from this function, called on every one of the three new rejection paths) deletes an on-disk snooze-marker file via `std::sys::fs::remove_file`, so a rejected confirm does not leave the user stuck in a suppressed/snoozed suggestion state.
8. A conditional "daemon self-repair" sub-path was found inside the new `load_local_state_synced` call: `check_daemon_state` → `resolve_daemon_binary` → `install_daemon`, and on install failure an internal (non-user-facing) diagnostic string `"AUTO_SWITCH_DAEMON_REPAIR_FAILED"` is formatted and appended to a Vec<String> log carried in the returned state. This does not itself fail `confirm_pending_auto_switch`.

## Inferred (plausible reading of the decompiled control flow, not independently confirmed by a second method)

1. The two packed fields tested at the matched-candidate offset (`+128` discriminant compared to `2`, `+168` bitfield masked `&0xFE` compared to `2`) are read as "does this candidate need an OAuth freshness re-check" — plausibly an account-kind/state enum (removed vs active) combined with an auth-type bit (OAuth vs API-key), but the exact enum/bitfield semantics were not independently cross-checked against a struct definition this round.
2. `Repository::clear_auto_switch_transient_state` (called from `switch_account`, VA 0x100534d40) is inferred to clear whatever transient candidate/suggestion state this new freshness-gate machinery introduces, by name and calling-context proximity to the new gate; its own body was not decompiled this round.
3. `token_remaining_seconds` (called first inside `ensure_fresh_token`) is inferred to be a fast-path TTL check that may allow skipping the network round-trip entirely when the current token is still comfortably valid; the exact threshold and branch were not traced.
4. `sync_local_runtime_state` and `load_local_state` (both pre-existing `Repository` methods, called from the new `load_local_state_synced` call site) are inferred to be unchanged pre-existing subsystem code reused from a new call site, based on the thread-model survey's earlier finding that core daemon/LaunchAgent machinery is "confirmed unchanged" between 1.0.9 and 1.1.8 — but their bodies were not independently re-decompiled and re-diffed this round.
5. The permissive fallback on `load_auth_file` failure (switch proceeds without a freshness check when the auth file can't even be loaded) is inferred to be an intentional "don't block the user on an auth-file read error" design choice rather than a bug, based on the surrounding error-handling style (every other failure mode in this function produces an explicit user-facing error), but this was not confirmed against any design doc or commit message.
