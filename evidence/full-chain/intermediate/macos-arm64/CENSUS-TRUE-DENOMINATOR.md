# AiMaMi 1.2.3 macOS-arm64 — True Denominator Census

Generated by an in-process idapython script (`IDA Python`) run directly on the
IDA host (`<host>`, module `AiMaMi`, `IDA decompiler_ready=true`, verified via
`server_health` per IDA_LIVE_GATE before every run). Script + raw run log kept
alongside this report: `_census_script.py`, `_census_run.log`,
`CENSUS-TRUE-DENOMINATOR.summary.json`. Per-function machine-readable output:
`CENSUS-TRUE-DENOMINATOR.jsonl` (4160 lines, one JSON object per function).

## 0. What was wrong with the previous population=4160 claim

The prior pass counted **every** `idautils.Functions()` entry whose demangled
name contains `codexmate_lib` as one unit of "work to reverse", then bucketed
by the first 3 `::`-segments. That inflated the denominator two ways that this
census corrects:

1. **`drop_in_place<...>` destructor thunks counted as if they were the async
   command body.** E.g. `commands::skills` "46 functions" and
   `commands::analytics` "36 functions" were **100% `core::ptr::drop_in_place<
   tokio::runtime::task::core::{Stage,CoreStage}<tokio::runtime::blocking::
   task::BlockingTask<codexmate_lib::commands::...::{{closure}}>>>` destructor
   stubs** — verified directly in this run (see §3). None of them are call-
   able business logic; they only run when the spawned task's future is
   dropped.
2. **Legacy Rust mangling artifacts (`..` separators, `$LT$`/`$u7b$` escapes)
   were left un-decoded**, which silently broke every name-based
   shim→real-body resolution attempt in the prior pass (the raw string never
   matched a clean `codexmate_lib::...::{{closure}}` symbol because of the
   un-decoded escapes). This census decodes them (`decode_legacy_mangling`)
   before any classification runs.

A first version of this very census script had its own bug: a naive
`rstrip('>')`/`rstrip('}')` on the extracted inner generic argument broke on
nested wrappers (`drop_in_place<BlockingTask<codexmate_lib::...>>`), which
caused **every** unresolved `drop_in_place` shim to fall through into
`genuinely_inlined` (2297 of them) with no real evidence — exactly the
"unknown washed into inlined" anti-pattern the skill's red line 13 forbids.
That was caught, fixed with a proper `<`/`>` depth-counter (§ script), and a
mandatory **decompile confirmation gate** was added so `genuinely_inlined` can
only be set when Hex-Rays decompile of the shim itself is available, not
truncated, and shows no unexplained non-drop/non-dealloc calls. Final run:
`genuinely_inlined=13` (down from the buggy 2297), `unknown=1750` (the honest,
conservative bucket).

## 1. Method (four-way classification, run inside IDA over all 4160 symbols)

For every function in `idautils.Functions()` whose demangled name contains
`codexmate_lib` (after legacy-mangling decode):

- **`real_body`** — not an IDA-flagged thunk, not a `drop_in_place<...>`
  pattern → treated as a genuine function body (this includes ordinary
  functions, `{{closure}}` bodies, `<T as Future>::poll` bodies, trait impls).
- **`shim_with_real_body_elsewhere`** — either (a) IDA-flagged `FUNC_THUNK`
  resolved via `ida_funcs.calc_thunk_func_target`, or (b) a
  `drop_in_place<...>` wrapper whose inner generic-argument type was extracted
  with a `<`/`>` depth counter (handles arbitrary nesting) and matched by name
  against another non-`drop_in_place` symbol in the population (preferring
  `::poll` > `call_once`/`call_mut` > `{{closure}}` > other), or (c) resolved
  by scanning the shim's own disassembly-level callees (`CodeRefsFrom`) for a
  non-`drop_in_place` `codexmate_lib` callee. The resolved target address is
  recorded (`real_body_addr`) — this satisfies the "must point to a real body,
  not stop at the shim" rule. The resolved target is **not** double-counted:
  it is independently classified on its own turn in the same enumeration.
- **`genuinely_inlined`** — only when name-search AND callee-scan both found
  nothing, **and** a direct Hex-Rays `decompile()` of the shim succeeds
  (non-truncated) and shows ≤25 pseudocode lines with ≤2 calls that aren't
  drop/dealloc/panic plumbing. Evidence text (line count + call list) is
  recorded per item.
- **`unknown`** — everything else: decompile failed/errored/truncated, or
  decompile succeeded but showed unexplained extra logic that couldn't be
  attributed. **Always counted as gap** (never silently dropped from the
  denominator).

Disk cross-check is **by address**, not filename: every `*_0x<addr>.c` under
`raw/aimami/1.2.3/macos-arm64/**` had its address extracted into a set; a
function counts "on disk" only if its own address is in that set.

**True denominator = `real_body_total + unknown_total`.** `unknown` is folded
into the denominator (not excluded) because the task's own instruction is
explicit: unresolved items "计入缺口" (count as gap) — excluding them would
hide gap size and inflate the reported coverage%. `shim` and confirmed
`genuinely_inlined` are excluded from the denominator because their business
logic is either already counted at another address, or confirmed (via
decompile) to have no separate address to reverse.

## 3. Verified examples (the exact pattern the task cited)

`commands::skills` (46 items) and `commands::analytics` (36 items) are **100%
`unknown`** in this census — i.e. this pass could not mechanically prove they
are inlined-away glue, so they still count as gap (conservative, not "洗白"),
but direct inspection during this run turned up strong circumstantial
evidence that most are thin async-dispatch wrappers whose real logic already
lives in the sibling `core::*` module and is already counted there. Example
(`commands::skills::import_skill`):

```
unknown | 0x100016a60 | core::ptr::drop_in_place<tokio::runtime::task::core::Stage<
          tokio::runtime::blocking::task::BlockingTask<
          codexmate_lib::commands::skills::import_skill::{{closure}}::{{closure}}>>>
unknown | 0x100019c00 | ...CoreStage<...BlockingTask<...import_skill::{{closure}}...>>>
unknown | 0x100021d70 | ...Box<Cell<...BlockingTask<...import_skill::{{closure}}...>>>>
real_body | 0x10034a3c0 | codexmate_lib::core::skills::import_skill                  (on disk)
real_body | 0x10034b780 | codexmate_lib::core::skills::import_skill::_{{closure}}    (on disk)
real_body | 0x10034b8a0 | codexmate_lib::core::skills::import_skill::_{{closure}}    (on disk)
```

A cross-reference pass (`commands::<sub>::<fn>` unknown → does
`core::<sub>::<fn>` exist as a confirmed `real_body`?) found **72 of the 372
`commands::*` unknowns** match this pattern exactly:
`commands::skills` 46/46, `commands::sessions` 25/28, `commands::debug_bundle`
1/3. `commands::analytics`'s 36 unknowns did **not** match by this naming
heuristic (no identically-named `core::analytics::<fn>` sibling found) — those
remain unexplained and should be prioritized for manual/LLM-assisted
caller-disambiguation (per the skill's `ida-deep-recovery.md` playbook) before
being written off.

**This cross-reference is reported as context only — it was not applied to
the headline `unknown=1750` count**, because it only proves a same-named
sibling function *exists*, not that the wrapper closure calls it (that
requires the caller-disambiguation the anti-cheat playbook mandates, which
this automated census pass did not perform per-item at this scale).

## 4. Largest single flagged caveat: `run::{{closure}}` bucket (614 items, true_gap=610)

The single largest "module" bucket by raw count is
`codexmate_lib::run::{{closure}}` — 614 population items, **all but 4 are
`unknown`** (the other 4 are `shim_with_real_body_elsewhere`). Sampling shows
these are exclusively `drop_in_place<codexmate_lib::run::{{closure}}::
{{closure}}::{{closure}}>` chains, i.e. destructor stubs for **anonymous
closures nested 2-3 levels deep directly inside the app's top-level `run()`
bootstrap function** — the shape strongly matches Tauri's auto-generated
`invoke_handler`/command-registration dispatch machinery (one wrapper closure
per registered `#[tauri::command]`), not hand-written business logic. If that
hypothesis holds, most of this 610 is dispatch boilerplate whose real logic is
each command's own already-separately-counted function, not a genuine 610-
function reversal backlog. **This was not verified per-item in this pass**
(would require the same caller-disambiguation as §3) and is reported as a
flagged follow-up priority, not folded into the headline numbers.

## 6. Known residual noise in this census (small, documented, not silently hidden)

- A handful of `run::{{closure}}...` module labels above are duplicated with
  mangled-hash/leftover-bracket text appended (marked *mis-split residual*).
  Root cause: the module-bucketing depth-counter used for `module_of()` is
  the simpler "first 3 `::`-segments" splitter (not the same corrected
  depth-counter used for shim resolution in §1); for a few deeply-nested
  anonymous-closure names it produces a stray bucket instead of merging into
  `codexmate_lib::run::{{closure}}`. Combined true_gap impact: 5 items — noted
  here rather than silently merged, per the no-hidden-cheat rule.
- 3 on-disk `.c` files (by address) don't correspond to any function in the
  `codexmate_lib` population (`disk_addr_extracted_count`=1652 vs
  `on_disk_by_addr_total`=1649 for `real_body`) — likely dumps of non-
  `codexmate_lib`-named functions or stale files; not investigated further in
  this pass.
- 10 `.c` filenames on disk didn't match the `_0x<addr>.c` naming convention
  and were excluded from the disk-address set (out of 1662 total `.c` files).
- `unknown` items each carry a `recovery_attempts` array in the `.jsonl`
  (name-search result, callee-scan result, decompile-trivia-check verdict)
  for auditability — nothing was marked `unknown` without a recorded attempt.
